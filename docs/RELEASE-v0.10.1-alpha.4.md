# v0.10.1-alpha.4 — 修复空白号「所有可改装武器缺改装按钮」（补改装条目）

> 2026-11-26 · 预发布（alpha）· 纯 bug 修复（`0.10.1-alpha.3` → `0.10.1-alpha.4`）
>
> 实机反馈（空白号，alpha.3）：改装按钮**仍然全部缺失**。

## 决定性反例（你给的）

> 「仍缺失。反例：保持全解锁代理打开，换主号，"改装"按钮正常。」

同一代理、同一份注入，**主号正常、空白号全缺** ⇒ 不是注入量、不是 4096 上限、不是 `isDiscovered`，
而是**该账号在这条数据上的服务端状态**差异。alpha.3 之前所有"补量"方向的尝试因此全部作废。

## 定位（同一会话两个号的原始抓包，注入完全相同）

| 端点 | 主号 | 空白号 |
|---|---|---|
| `GET /api/Progression/Items/Customize/v2` | **74 条 / 15853 B** | **`{"items":[]}` / 12 B** |
| `GET /api/Progression/inventory` → `customization[]` | **149 条** | **1 条** |

- 这是两个号**唯一仍然不同的「改装」相关数据**（库存 970→3100 / 60→3098 行、`packageProgress` 56 条包，
  注入后两边一致；目录、`ProgressionPackages`、舰船模块等级亦一致）。
- 客户端在启动 **+18 s**（inventory）与 **+19 s**（Customize/v2）各拉一次，**整局不再重取** ⇒
  空白号整局手里都没有"哪些武器可改装"的清单。
- 这两个响应是**客户端自己 PUT 过的真实结构**：空槽条目长这样
  （`f71b1f23_*`，空白号自己发出去的那条）：
  `{"mixId32":<武器>, "modes":[], "activeIndex":0, "customizations":[{"index":0,"slots":[0,0,0,0,0,0,0,0]}]}`

## 修法（仍只改客户端收到的响应）

一键解锁开启时，按**运行期客户端目录**找出「**带附件子项的 pc1 武器**」（本 build 真机 **57 把**），
给每把补一条**空槽**条目，两个响应都喂：

- `Items/Customize/v2`：`{mixId32, modes: [], activeIndex: 0, customizations: [{index: 0, slots: [0]*8}]}`
- `inventory.customization[]`：`{mixId32, index: 0, activeIndex: 0, slots: [0]*8, modes: []}`

**边界与安全**

- 只补「目录里有附件子项」的武器：HellForge `RegisteredItems.cs:14-17` 记录改装界面按
  `WeaponChild(attachment, weapon)` 重算子项，「没有子项 + 没有精通包的武器会让该界面崩」⇒ 不该进这份数据。
- **玩家已有的真实预设一律不动**：主号 74 条原样保留，只补缺的 5 条；空白号 0 → 57 条。
- 幂等：同一响应重复处理不会重复追加（单测覆盖）。
- 空槽 = 客户端自己的初始态（`slots` 全 0），不改任何配件数值、不写服务端。
