# v0.5.4-alpha.1 — 存档层 G5 收尾：局内消耗扣减（2026-11-23）

> **功能版本**：`X.Y.Z` 变化（`0.5.3-alpha.1` → **`0.5.4-alpha.1`**）。

## 背景

`0.5.2-alpha.1` 已做完 G5 的"成就上报合并"；G5 的另一半是**局内消耗扣减**，当时因为缺少请求体形状而暂缓。
研究线 2026-11-23 给了明确口径，本版按"两段式"先落实现（形状确认后只改解析器）。

## 这版做了什么

`POST /api/Progression/inventory/consume` 的**请求体** → 本机库存扣减：

```
请求体（防御式解析）  {mixId, amount} → inventory_amounts[mixId] -= amount（下限 0）
```

### 扣减口径（逐条对齐研究线）

| 规则 | 理由 |
|---|---|
| **下限 0** | 消耗不能把数量扣成负数 |
| **保留行、`amount=0` 不删行** | 库存行同时承担"是否拥有该物品"的语义（目录行 + 库存行成对才显示），删行可能让物品从军械库消失；服务端是否删行无样本，保留是安全默认 |
| 只扣**已跟踪**的 mixId | 本机账本里没有它的基线数量 —— 宁可不扣，也不凭空造数字 |
| 形状不认识**不扣** | 同成就的策略：不猜 |
| 每次扣减打 **INFO** | `CONSUME mixId=… amount=…：存档 A → B（mission …）`，与结算入账串起来对账 |
| 走 `update_earned()` | 自动参与会话基准回滚 / `identity_strict` 拒写 / orphan 审计 |

### 两段式解析（为什么现在就能实现）

研究线会在一次本地游戏会话里补采真实请求体形状（`inventory/consume` + `Achievements` 两个端点，
约 10 分钟）。本版先按**防御式**解析实现：

- 外壳：`{"items":[…]}` / `[…]` / `{"consumables":[…]}` / `{"entries":[…]}` / 单条目摊平；
- 行内：`{mixId | mixId32, amount}`，非法行跳过；
- 解析不出来 → **不扣** + 一条可操作日志。

得到真实形状后只需改 `hooks/consume.py` 的解析器（与成就同样的"确认形状 + 保留兜底"做法），不动扣减逻辑。

## 边界（写清，避免误解）

- 本机账本只记录"经过本机存档层的数量"（任务奖励 + 已跟踪基线）。**没跟踪的物品消耗会被跳过**并打 INFO ——
  这是有意的保守：服务端真实库存不可读，凭空造数量会导致显示错乱。
- 消耗响应不改写（响应本来就是 `{}`），所以**游戏内表现完全由服务端/客户端决定**；
  本机账本的变化在**下次启动**合并 `Progression/inventory` 时体现（与 G2 的刷新时序一致）。

  未跟踪跳过 / 无变化不写盘 / 未识别不写盘 / strict 拒写 / INFO 日志（含 missionId）/ 扣到 0 后库存响应仍为 0；

## 兼容性

- 存档 `schema v2` 不变；无 profile / 控制面协议变化；
- 实机待验：消耗品（如战备/投掷物）用掉后，**重启**游戏看数量是否按扣减后的账本显示。
